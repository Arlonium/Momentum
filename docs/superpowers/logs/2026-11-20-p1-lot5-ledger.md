- **Ruling R1250** : R1236 tient (sans état, un message par `POST`, réponse JSON, ni session ni flux, pas de SDK), et **les deux révisions restent servies**, la 2026-07-28 d'abord ; L17 est confirmée — un vrai Claude Code (2.1.329, runtime MCP « v2 » par défaut) sonde par `server/discover`, parle la 2026-07-28 avec tous les en-têtes et le `_meta` voulus, n'ouvre ni session, ni `GET`, ni `subscriptions/listen` sans `listChanged`, et retombe seul sur `initialize` devant un serveur de la seule 2025-11-25 ; forcé en 2025-11-25 (`MCP_PROTOCOL_NEGOTIATION=legacy`, ce que parlent ses versions d'avant le runtime « v2 » et les clients sur le SDK 1.x), il échoue devant un serveur de la seule 2026-07-28 (`400`, `-32022`, « Connection failed ») — une table de cas deux fois plus grande en M1 ; si aucun client de la seule 2025-11-25 ne reste, retirer cette ère est une branche à supprimer.
- **Ruling R1251** : la table de cas de M1 prend les formes relevées dans la spécification et chez Claude Code : `-32022` (`UnsupportedProtocolVersion`, `data: { supported, requested }`) pour une version non servie ; `-32020` pour un en-tête absent ou qui ne dit pas le corps (`MCP-Protocol-Version` absent compris) ; `400` et `-32602` pour un `_meta` sans `clientCapabilities` ; `-32602` pour un outil inconnu et pour une ressource inconnue en 2026-07-28 (`data: { uri }`), `-32002` en 2025-11-25 ; `ttlMs` et `cacheScope` sur `server/discover` aussi ; les clés inconnues de `_meta` ignorées (`progressToken`, `claudecode/toolUseId`) ; `resources/list` servi dans les deux ères (Claude Code le demande à chaque connexion) ; `GET /mcp` en `405` (le client 2025-11-25 l'ouvre après `initialize` et l'accepte) ; un `401` avec `WWW-Authenticate: Bearer`, sans métadonnées OAuth ni adresse `/.well-known/…` (E7 ; Claude Code n'en demande aucune quand un `Authorization` est configuré) ; les requêtes réelles de Claude Code relevées par S0 entrent telles quelles dans la table — c'est ce que la spécification exige, et ce qu'un vrai client envoie — un client qui exigerait les métadonnées OAuth ne se branche pas (LA-h).
- **Ruling R1252** : `401 invalid_token` garde son corps et son message (R1215), mais la recette juge le message que Claude Code montre au modèle, pas le nôtre : Claude Code ne lit au modèle le corps d'aucun `401` ; à la connexion il échoue sans repli sur OAuth (« Server rejected the configured Authorization header (HTTP 401) »), en cours de session le modèle lit « rejected the Authorization header in its config (update it, then run /mcp to reconnect) » ; une erreur JSON-RPC d'un `tools/call`, elle, est lue au modèle telle quelle (vu avec `-32020`) — les messages de refus d'un outil (R1240) atteignent bien le modèle, ceux du jeton non — si un autre client montre le corps d'un `401`, le message de R1215 le sert.
- **Ruling R1253** : la commande prête à coller de C1 porte `--header 'Authorization: Bearer ${MEMENTUM_TOKEN}'` entre apostrophes, et l'écran dit que la variable doit être posée à chaque lancement de Claude Code, et que la forme entre guillemets garde le jeton en clair dans la configuration de Claude Code — S0 a vu Claude Code développer `${BANC_TOKEN}` et `${MEMENTUM_TOKEN}` à chaque lancement depuis une configuration donnée par `--mcp-config` (16 caractères reçus), et le nom en `…_TOKEN` n'est pas vidé comme une variable « de secret » ; ce que `claude mcp add` écrit de l'en-tête n'a pas été essayé (la tâche ne devait pas écrire dans la configuration de Claude Code de l'utilisateur) — si `claude mcp add` développe la variable lui-même, la phrase de l'écran est fausse : la fin du lot le vérifie (point 4), et C1 la corrige.
- **Ruling R1254** *(précisé par S2, R1280 et R1284 : les deux transactions ne se mettent pas bout à bout comme dans `write_all` dès qu'un attribut est écrasé, leurs jeux de suppressions se fondent ; « ne le rejoint que pour un ordre entièrement renversé » est faux : des paires voisines échangées coûtent 1,17 fois `rewrite_blocks`, et des milliers de blocs retirés à part croissent plus vite que la page ; aucun seuil, toujours)* : `write_diff` n'a **aucun seuil par part de blocs touchés** ; il écrit **toujours en deux transactions** (les suppressions, puis les écritures, mises bout à bout comme dans `write_all`) ; il ne retombe sur `rewrite_blocks` que pour une page que `read_blocks` normalise (ses éléments Yjs ne répondent pas un à un à ses blocs) — sur 10 000 paragraphes, la différence coûte 47 à 51 ms pour un bloc changé, inséré, retiré ou déplacé, 62 ms pour la moitié changée, 75 ms pour tous, contre 625 à 650 ms pour `rewrite_blocks`, ne le rejoint que pour un ordre entièrement renversé (640 contre 654 ms) et reste deux fois plus rapide quand la page double par insertions (2,1 contre 4,3 s) ; en une transaction, un contenu retiré du même client coûtait jusqu'à 3,6 fois plus (ordre renversé 2,3 s, page à six plages entièrement changée 950 ms contre 700 ms pour `rewrite_blocks`) ; un bloc intact n'est jamais touché, vérifié élément par élément sur la fixture `all-blocks` — un seuil aurait fait perdre toute frappe concurrente sans rien faire gagner ; si une forme de page non mesurée (des milliers de déplacements entremêlés d'insertions) coûte plus que `rewrite_blocks`, `diff_cost` la borne, et un repli par coût estimé se pose alors, avec sa mesure.
- **Ruling R1255** : un contenu en ligne changé s'écrit **par préfixe et suffixe communs** quand le milieu changé tient dans un seul `XmlText` et ne porte aucun élément en ligne (mention, formule, saut de ligne), des deux côtés, et **en entier** sinon (un tableau changé aussi) — sur 9 scènes et 198 combinaisons avec des frappes concurrentes du vrai Yjs (13.6.33), l'écriture se lit comme voulu, les 90 frappes hors du texte remplacé sont gardées (la récriture en entier en perd 72 sur 72), et Yjs lit comme yrs sauf une fois, où Yjs nettoie de lui-même des marqueurs de format (`cleanupYTextAfterTransaction`, transaction locale qu'un navigateur renvoie) et où yrs, ce nettoyage reçu, lit comme lui ; le surcoût est de 1 à 3 fois l'écriture en entier, toujours loin sous `rewrite_blocks` (5 000 blocs changés : 177 contre 64 ms) — chaque navigateur qui reçoit un changement de marques ainsi écrit renvoie un nettoyage (une écriture de plus par onglet ouvert) ; un changement de marques seules par `format`, comme y-prosemirror, l'éviterait peut-être : non mesuré, à S2.
- **Ruling R1256** : une route d'une page juge une page par jeton par la **remontée de ses parents visibles** jusqu'à une page de la portée, sur le calcul du compte, puis ramène son niveau et pose l'interdit (au même résultat que `narrowed`, que tient un test de propriétés) ; la restriction entière ne sert qu'aux routes de tout l'espace, avec le rang du parent visible gardé dans `SpaceAccess` ; pas de cache de la restriction — prototype : la restriction entière coûte 2,2 ms au p50 (2,5 au p95) sur 10 000 pages et 30 ms (31) sur 100 000 quelle que soit la portée, presque le calcul du compte (2,7 et 37 ms), si bien que le `404` d'une page hors portée coûtait 2 à 30 ms de plus que celui d'une page inconnue ; la remontée coûte 10 à 20 µs aux deux tailles ; avec les rangs, la restriction entière tombe à 0,15 ms (p95 0,35) et 2 ms (p95 2,4), sous le seuil de 1 ms de R1217 — les rangs ajoutent 4 octets par page au cache des accès et jusqu'à 12 ms au calcul de 100 000 pages tel que mesuré (moins s'ils viennent de la table que `compute` bâtit déjà) ; S5 remesure dans le serveur.
- **Ruling R1257** : la version `before_agent` est relue (`check_state`) et écrite **hors de l'acteur dès S4**, comme la compaction (R826) ; l'acteur n'encode que l'état, et l'opération destructrice s'applique dans une seconde commande, une fois la version écrite, si ce qu'elle remplace n'a pas changé depuis l'état encodé (sinon une seconde coupe, puis `409 version_refused`) — encodage, relecture et écriture de suite : 147 ms au p50, 160 au p95, pour la page de 10 000 paragraphes des budgets (7,7 + 112 + 29 ms) ; 306 ms pour 10 000 paragraphes à six plages (19 + 249 + 38 ms) ; tenus par l'acteur, ils font attendre toute frappe au-delà de son budget de 150 ms (l'ancien chiffre de R1234, 120 ms, venait de R816 : la relecture vaut ici 112 ms, non 81) — deux commandes et une revérification à écrire en S4 ; l'appel de l'agent attend 150 à 300 ms de plus.
- **Ruling R1258** : un vrai Claude Code, dans une tâche ou à la fin du lot, se lance **en mode non interactif**, avec une configuration à part (`claude -p … --mcp-config <fichier> --strict-mcp-config --tools "" --allowedTools <outils> --no-session-persistence --setting-sources project`), un jeton factice ou de test dans une variable, sur `127.0.0.1` et un port à la tâche, jamais par `claude mcp add` ni rien qui écrive dans sa configuration de l'utilisateur ; chaque lancement compte sur le compte de l'utilisateur : quelques-uns au plus — c'est la forme que S0 a suivie (neuf lancements, `~/.claude.json` sans trace du banc après eux) — ce qu'écrit `claude mcp add` ne se voit alors que par Alex (R1253).

## Task M1 : `mementum-mcp`, le protocole et les outils, sans réseau (2026-11-20)

Intègre les précisions de la relecture des mesures de S0 (plan corrigé l. 173 et E8). Tests :

- **Ruling R1405** : l'API que M2 appelle est `serve(&Headers, body, Endpoint, &impl Host) -> Served { reply, call }` (l'issue d'un `tools/call` depuis la relecture de M1, R1560) ; en dessous, `protocol::read(&Headers, body, Endpoint) -> Result<Incoming, Box<Refused>>` (`Incoming { era, id, request }`, là où le plan écrivait `(Era, Request)` : l'`id` sert à la réponse) et `protocol::write(era, &Id, Answer) -> Reply` ; `Headers` porte **toutes** les valeurs reçues de `MCP-Protocol-Version`, `Mcp-Method` et `Mcp-Name` (une liste vide : absent ; plusieurs : répété, donc refusé) ; `Host` n'a qu'une méthode, `call(ToolCall) -> impl Future<Output = ToolOutput> + Send`, et `ToolOutput` ne se bâtit que par `text::` — une seule entrée pour la route, un `match` exhaustif sur les six outils côté serveur, et aucune sortie non bornée possible — l'issue d'un appel pour le journal d'activité est rendue par `serve` (R1560), refus d'avant l'hôte compris.
- **Ruling R1406** : statut HTTP d'une erreur JSON-RPC : `400` pour ce qui empêche de lire la requête ou d'en savoir l'ère (`-32700`, `-32600`, `-32020`, `-32022`, et `-32602` d'un champ exigé du `_meta`), `404` pour une méthode inconnue en 2026-07-28, **`200` pour une erreur des params d'une méthode servie** (`-32602` : outil inconnu, outil d'écriture sur `/mcp/readonly`, `tools/call` sans nom, arguments qui ne sont pas un objet, ressource inconnue en 2026-07-28, curseur de liste, `initialize` sans `protocolVersion` ; `-32002` : ressource inconnue en 2025-11-25) et pour une méthode inconnue en 2025-11-25 ; des arguments refusés sont un résultat `isError` (`invalid_arguments`), `200` — ni la spécification ni le plan ne fixent le statut d'un `-32602` (relecture de S0) ; le banc rendait `200` et Claude Code a lu l'erreur ; `400` reste « la requête ne se lit pas » — un client qui attendrait un `4xx` pour un outil inconnu verrait un `200` : une ligne par code dans `protocol.rs`.
- **Ruling R1407** (relecture des mesures de S0) : une requête qui n'est d'aucune révision, ou sans en-tête `MCP-Protocol-Version`, reçoit `400` et `HeaderMismatch` (`-32020`), par la validation des en-têtes ; `-32022` reste pour une version **nommée** mais non servie : au `_meta` (tout texte, `2025-11-25` compris, que le serveur ne sert que par `initialize`), ou par l'en-tête seul quand il a la forme `AAAA-MM-JJ` (`data.supported` liste les deux révisions) ; un en-tête `2026-07-28` sans version au `_meta` et un en-tête qui n'a pas la forme d'une version sont des `-32020` ; une version du `_meta` qui n'est pas un texte est un champ exigé sans sa forme, `400` et `-32602` — c'est ce que dit la spécification (plan, R1236, corrigé l. 173) ; `-32021` (`MissingRequiredClientCapability`) n'a pas d'usage ici, aucun outil n'exigeant une capacité du client — un client d'avant la 2025-06-18 lit un `-32020` au lieu d'un `-32022` : il ne se branchait pas davantage.
- **Ruling R1408** : une notification (sans `id`) dont la méthode commence par `notifications/` reçoit `202` sans corps, dans les deux ères (en 2026-07-28, après le jugement de la version et de `MCP-Protocol-Version` ; `Mcp-Method` et `Mcp-Name` ne sont pas jugés, la révision ne définissant pas les en-têtes d'une notification) ; toute autre méthode sans `id` reçoit `400` et `-32600`, et **n'est jamais faite** — un `tools/call` sans `id` écrirait sans que personne lise la réponse — un client qui enverrait une requête sans `id` en attendant qu'elle se fasse est refusé. *(Complété à la relecture de M1, M4 : une `notifications/…` sous l'en-tête `MCP-Protocol-Version: 2026-07-28` reçoit `202` même sans `_meta`.)*
- **Ruling R1409** : l'enveloppe se juge avant l'ère, et rien ne recopie l'entrée : un lot se reconnaît à son premier caractère non blanc (`[`) et est refusé sans être lu ; un `id` est un texte de 256 octets au plus ou un nombre, sinon `-32600` avec `id: null` (la réponse le recopie) ; `params` qui n'est pas un objet, ou une réponse JSON-RPC envoyée au serveur, `-32600` ; toute valeur du client recopiée (méthode, nom d'outil, adresse de ressource, version de `data.requested`, valeur d'un en-tête, champ d'un argument refusé) passe par `mementum_md::excerpt` — R380, R434 ; linéarité mesurée à 4 Mio (pic au plus 11 octets par octet d'entrée sur onze formes, réponses de 4 Kio au plus) — un `id` de plus de 256 octets, permis par JSON-RPC, est refusé. *(Complété à la relecture de M1, M11 et M12 : un `id` numérique doit être entier, un `1.5` reçoit `-32600` ; la forme « imbriquée » du test de linéarité est faite d'objets, un `[` en tête étant refusé comme un lot sans être lu.)*
- **Ruling R1410** : en 2025-11-25, `Mcp-Method` et `Mcp-Name` ne sont pas jugés ; `initialize` ignore l'en-tête `MCP-Protocol-Version`, rend toujours `2025-11-25` quelle que soit la version demandée (la négociation de cette révision), et exige un `protocolVersion` en texte (`-32602` sinon) ; `ping` rend `{}` — c'est la révision telle qu'un SDK 1.x la parle — un client dont le SDK précède la 2025-11-25 reçoit `2025-11-25` à `initialize` et se déconnecte *(coût récrit à la relecture de M1, M10 ; servir aussi la 2025-06-18 est la décision L18 du plan, « non au lot 5 » par défaut)*.
- **Ruling R1411** : `tools/list`, `resources/list` et `resources/templates/list` rendent tout, sans `nextCursor` ; `resources/templates/list` rend une liste vide (`ttlMs` et `cacheScope` en 2026-07-28, comme toute liste ; ajouté à la relecture de M1, M13) ; un `cursor` reçu (que le serveur ne donne jamais) est `-32602` — la spécification demande `-32602` pour un curseur invalide, et un client qui demande les modèles de ressources ne doit pas recevoir une méthode inconnue — rien.

- **Ruling R1280** : `DiffWritten { update, touched, fell_back }` porte **une seule mise à jour** : les éléments de la seconde transaction (les écritures), suivis du jeu de suppressions des deux (`IdSet::merge`, réencodé) ; les attributs retirés vont dans la première transaction (`remove_attribute`), les attributs écrasés dans la seconde, qui supprime leur ancienne entrée ; la première ne doit rien créer (`HalfWritten` sinon, page à recharger).
